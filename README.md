# HoshiDrink

一个离线使用的 Android 饮水提醒应用，支持 Android 8.0 及以上。

## 技术

- Kotlin、Jetpack Compose、Material 3：原生界面与动态水位。
- ViewModel、StateFlow、Coroutines：界面状态与后台数据读写。
- SQLite：饮水记录；SharedPreferences：目标和提醒偏好。
- AlarmManager、WorkManager、Notification API：系统闹钟、后台兜底与系统通知。

无需服务器、账号或网络权限。准时提醒为可选功能，Android 12+ 需用户允许“闹钟和提醒”权限。

## 功能

- 今日饮水量、完成比例、动态水瓶、剩余目标。
- 150 / 250 / 350 mL 快捷选择，1–2000 mL 自定义容量。
- 今日及历史记录，删除与撤销。
- 最近七天统计，前后翻页，按日期查看明细。
- 500–6000 mL 每日目标。
- 30 / 60 / 90 / 120 分钟提醒间隔，以开始时间对齐，结束时间不提醒，支持达标暂停。
- “10:00–18:30 整点震动”一键预设，每日提醒时刻预览。
- Android 13+ 通知权限申请及系统通知设置入口。
- 仅响铃、响铃和震动、仅震动、静音四种通知方式，以及试发提醒。
- 震动提醒默认兼容手机静音模式，无需单独开启开关。
- “仅震动”支持可选持续震动，可从通知按钮、通知入口、应用内按钮或记水操作停止。
- 可选准时提醒、闹钟权限状态、电池优化与后台设置入口。
- 空数据状态、跨日刷新、应用重启后数据保留。

## 构建

使用 Android Studio 打开本目录，安装 Android SDK 36，使用 JDK 17 或更高版本。
Android Studio 会生成 `local.properties`；命令行也可以设置 `ANDROID_HOME`。

```sh
./gradlew assembleDebug testDebugUnitTest lintDebug
```

安装包：`app/build/outputs/apk/debug/app-debug.apk`。

```sh
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

## 提醒行为

首次使用默认关闭提醒。开启后，在允许通知的前提下，每隔设定时间发送一次系统通知，点击进入应用。
默认“仅响铃”沿用原版本通知渠道；可以切换“仅震动”等方式，并用“试发提醒”直接验证，无需等到下一次提醒。
每种方式使用独立的稳定通知渠道，因为 Android 8+ 不允许应用覆盖用户已配置的渠道声音和震动。
实际声音、震动、锁屏可见性由系统通知渠道与勿扰模式决定；试发提醒不启用定时提醒，也不改变下一次提醒时间。

“仅震动”或“响铃和震动”默认在手机静音时也请求震动，无需额外开关。系统处于静音模式时，
应用会发送无声音、无原生震动的通知，并通过 Vibrator 单独请求两段 250 ms 的震动，避免重复震动。
此请求使用闹钟用途的震动属性，以区别于被静音模式抑制的通知震动，不播放声音或更改手机模式。
仅在系统通知允许、渠道重要性至少为默认、渠道振动开启且勿扰关闭时使用；通知被关闭后不会单独震动。
应用在后台且手机处于正常响铃或振动模式时，单次提醒仍沿用通知渠道。试发与定时提醒使用同一权限检查。
厂商震动策略或系统闹钟震动强度设为零仍可能使请求无效，需要在真机确认。

“仅震动”下可打开“持续震动”（默认关闭）。使用 Android `VibrationEffect.createWaveform`
并指定循环索引 0，震约 400 ms 后停 1400 ms，循环至取消。支持振幅控制时使用渐强渐弱的波形。
持续震动由只在提醒期间运行的前台服务持有，含“停止震动”通知按钮；从任何入口进入应用、从系统清除该通知、
点击应用内“停止震动”、记录饮水、关闭持续震动或关闭提醒时会取消当前循环。
普通通知仍显示剩余饮水量；持续通知优先提供停止入口。试发提醒也使用相同循环，需要手动停止。
启用持续震动后，定时提醒在 App 前台和后台都启动相同的规律循环；App 已在前台不会跳过或缩短震动。
从后台进入 App 仍会停止当前循环，App 内可在设置页点击“停止震动”，也可使用通知上的停止按钮。
静音模式下同样支持持续震动；勿扰或通知渠道关闭震动时不启动循环。
服务与界面共用同一个震动实例，取消不依赖异步保存的布尔值；会话标识拦截已停止但排队中的旧启动。
勿扰或通知权限变化会结束当前循环。系统终止进程、重启或厂商震动策略仍可能提前结束循环。
Android 禁止某次后台前台服务启动时，退回普通通知及一次短震动，诊断中记录拒绝原因。

提醒以开始时间为基准，按间隔生成每天的固定时刻，包含开始时间、不包含结束时间。
记水或某次送达延迟后，下一次仍对齐这些固定时刻；不会改成从当下起重新倒计时。
重新打开应用、切换通知方式或准时模式会保留已有的本次任务；原版本的滚动倒计时会在升级后重新对齐。
达到目标后可暂停至次日开始时间。提醒时段限定在同一天内，结束时间必须晚于开始时间。

例如选择“10:00–18:30 整点震动”预设，时段为 10:00–18:30，间隔 60 分钟、仅震动、准时提醒，
且关闭达标暂停。开启提醒并允许所需权限后，每天计划在 10:00、11:00、12:00、13:00、14:00、
15:00、16:00、17:00、18:00 提醒，18:30 不提醒。当天中途开启时，从下一个固定时刻开始。

普通模式使用 `AlarmManager.setAndAllowWhileIdle`，比纯后台任务更适合用户可见的定时提醒。
开启“准时提醒”且具有权限时，使用 `setExactAndAllowWhileIdle`，可在 Doze 休眠时触发。
Android 12+ 必须由用户在系统页面允许“闹钟和提醒”；未授权时自动使用普通模式。
两种模式均安排在预定时间五分钟后的 WorkManager 任务作为兜底，实际执行仍可能延迟；持久化任务标识防止重复与过期通知。
升级时，原版本后台任务会迁移为新调度。重启、应用覆盖升级与时区/时间变化后会恢复或重新计算闹钟。
撤销精确闹钟权限会使 Android 取消精确闹钟；已有兜底任务可在系统允许执行时恢复普通提醒，重新打开应用也会立即重新调度。

精确闹钟不能绕过强行停止、系统勿扰、用户关闭通知或所有厂商后台限制，无法承诺绝不延迟。
可在设置中管理电池优化；华为等机型还可能需要在应用启动管理中允许自启动、关联启动和后台活动。
系统强行停止应用后，需要重新打开应用才能恢复任务。

设置 → 提醒可靠性可查看下次计划、实际精确/普通调度模式、复制最近 150 条事件，或导出完整 ZIP 日志。
日志默认开启，后台写入应用私有目录 `files/diagnostics/`，最多 7 个约 1 MiB 的 JSONL 文件，滚动覆盖最旧记录。
包含进程会话、日期时间与系统启动后时间、线程、异常堆栈（单条最多 24,000 字符）、任务/震动标识、系统状态和停止原因；不记录饮水明细，不自动上传。
连接手机后可运行 `bash scripts/collect-reminder-logs.sh`；指定设备和输出目录时用 `bash scripts/collect-reminder-logs.sh 设备序列号 输出目录`。
该脚本只读收集应用和相关系统状态，不会清空日志、杀进程或更改设置。正式签名包不允许 `run-as` 时，从应用中导出 ZIP。
详见[调研依据与故障排查](docs/reminder-investigation.md)。
提醒的实现原理、最初设计的问题和逐步调整过程，详见[饮水提醒是怎样实现和改好的](docs/reminder-reliability-postmortem-2026-11-03.md)。

所有统计按设备当前时区计算。达标天数按当前目标计算；日均为所显示七天的总量除以七。
数据仅存本机，卸载后清除。当前版本不含云同步、导入导出或医疗建议。
