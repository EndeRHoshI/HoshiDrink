# 饮水提醒是怎样实现的，又是怎样逐步改好的

日期：2026-11-03。

这个功能最终能用，靠的是两部分配合：应用正确安排提醒、控制震动，手机系统允许应用在后台被唤醒。
最初的实现没有把这两部分完整考虑进去，后面又出现了对前台行为的错误判断，才导致了几轮调整。

## 一、原理是什么

App 不需要一直开着界面，也不需要自己每秒检查时间。它提前把下一次提醒时间交给 Android，由系统负责计时。

一次提醒的过程是：

1. App 算出下一次提醒时间，例如 15:00。
2. 把这个时间登记到 Android 的闹钟服务。
3. 到时间后，Android 唤醒 App 的提醒处理代码。
4. App 显示通知，并按设置启动震动。
5. 用户进入 App、点“停止震动”或记录饮水，App 结束震动。

因此，“能到点提醒”和“能正确震动、停止”是不同的环节。之前两类问题都出现过，需要分别解决。

## 二、用什么实现闹钟

使用 Android 提供的 **`AlarmManager`（系统闹钟服务）**。

开启“准时提醒”且获得系统权限后，调用 `setExactAndAllowWhileIdle()`。它向系统请求在指定时刻触发，即使手机处于休眠状态，也允许执行这类提醒。

到点后，系统通过 `BroadcastReceiver`（广播接收器）通知应用处理。这里的广播不是网络消息，只是 Android 调用应用的一种方式。

时间安排也做过调整：最初按“从现在起隔一段时间”计算，不能自然满足你的整点要求；后来改为提前确定每天的固定时刻。
例如开始 10:00、结束 18:30、间隔 60 分钟，对应 10:00、11:00……18:00，18:30 不提醒。
即使某次晚到了，下一次仍按整点安排，不会跟着往后漂移。

另外用 `WorkManager`（系统后台任务）安排一份晚五分钟的兜底任务，给漏掉的提醒提供补发机会。
它也受系统省电限制，不能保证五分钟后必定补发；不是安排两次通知，正常情况下同一次提醒只处理一次。

**这里最初考虑不足的地方，是把“请求了精确闹钟”当成了可靠性的主要保障。**
实际上，手机厂商仍可能限制后台唤醒，应用拿到权限也不代表系统一定原样执行请求。后面的真机排查才把这一点确认清楚。

## 三、震动是怎样设置的

### 从通知震动，改为应用直接控制

最初使用通知自带的震动：创建通知时，告诉系统“这个通知需要震动”。
这个方案实现简单，但实际表现受手机的静音、振动模式和通知设置影响。你遇到的“必须打开振动模式才震动”，说明这个方案没有满足“静音时也震动”的要求。

后来改为通过 **`Vibrator`（震动控制 API）**直接请求震动，通知负责提供提醒内容和停止入口。
震动请求标记为 `USAGE_ALARM`，表示用于闹钟提醒，而不是普通通知反馈。它不播放声音，也不切换手机的响铃模式。

这仍然要尊重系统限制：通知或渠道被关闭、勿扰限制生效时，不强行启动震动。

### 从一次短震动，改为规律循环

你提出“规律震动直到按掉”后，使用 **`VibrationEffect.createWaveform()`** 定义循环波形：

**震约 0.4 秒 → 停约 1.4 秒 → 再震，重复执行，直到调用 `cancel()`。**

支持调节振幅的手机，会使用强弱变化的波形，让震感更柔和。循环交给系统执行，不是应用不停地重复发送震动命令。

为了让循环期间有明确的运行和停止入口，又增加了 **前台服务**。它在震动时显示一条带“停止震动”按钮的通知，震动结束后退出。
这里“前台服务”不等于必须打开 App 界面，也不是让应用全天常驻；它只在这次持续震动期间运行。

## 四、为什么一开始没有做好，又调整了什么

### 1. 我最初把“通知支持震动”理解得过于简单

最初的做法能让系统知道通知需要震动，但没有充分处理“手机静音，用户仍明确要求震动”的情况。
发现只有振动模式下才生效后，改为直接控制震动，并把它标记为闹钟用途。

得到的经验是：**先明确用户要的实际行为，再选择 API；不能只看某个开关或参数名字像是满足了需求。**

### 2. 我先完成了“开始震动”，没有把“结束震动”设计完整

早期只覆盖了点击特定通知进入 App 时的停止逻辑。但用户可能从桌面、最近任务或其他入口返回，这些入口不一定经过原来的处理路径。
另外，震动启动后，负责启动和取消的对象、状态也没有统一管理，增加了偶现问题的风险。

后来做了三项调整：

- 从任何入口恢复 App 界面，都执行停止处理。
- 始终通过同一个震动控制对象启动和取消。
- 给每次循环一个标识。用户停止后，这个标识立即失效；即使旧启动请求稍后才被处理，也不能重新开始震动。

得到的经验是：**持续执行的功能必须同时设计“怎么开始、谁负责、怎么结束”，不能把停止当成最后补一个按钮。**

旧版偶现时没有足够日志，无法证明每次失败都来自其中某一个问题；这些是检查代码后消除的具体缺陷和风险。

### 3. 为了避免“进入 App 后还震”，我又把前台判断做错了

我曾加入“App 在前台就不震动”的判断。这把两个不同场景混在了一起：

- 已经在后台震动，用户进入 App：应该停止已有提醒。
- 用户一直在 App 内，新的提醒时间到了：仍应该开始提醒。

错误判断导致通知到了，但震动被代码主动跳过。日志明确记录了“用户正在应用内”，当时根本没有发出震动请求。

随后我又先把前台行为改成短震动，这是我替你做了不符合要求的产品决定。你明确要求前台也持续规律震动后，才改成现在的行为。

现在分开处理：**到点时，前台和后台都可以开始持续震动；从后台进入 App 时，停止当前已经开始的震动。**

得到的经验是：**修一个问题时，应区分不同场景，保留已经明确的需求，不能用一个粗略条件把正常行为也禁止掉。**

### 4. 后台漏提醒，最后发现还有手机系统的限制

震动代码调整好后，你又发现“不打开 App 就不提醒”。这次没有继续凭现象修改震动代码，而是增加日志，并直接读取手机系统里的闹钟和后台任务状态。

结果发现：应用虽然提交了计划，但系统把原定 15:00 的闹钟额外延后了 3 天；兜底任务也受到系统管理。
13:00、14:00 的提醒都等到进入 App 后才处理，说明问题发生在系统唤醒应用之前。

随后你在手机上放开了后台、电池相关限制，并重新保存提醒。我再次读取系统状态，确认电池优化豁免已生效，3 天的额外偏移也消失了。
这部分是你操作的系统设置，不是我通过代码自动改掉的；由于多项设置一起调整，不能断言只有其中某一个开关起作用。

得到的经验是：**后台能力要在目标手机上验证。代码发出了请求，还要确认系统实际如何安排；兜底任务也不能假设不受同一套省电策略影响。**

## 五、最后验证到了什么结果

这次在你的一加手机上，完整过程已经对上：

| 环节 | 实际结果 |
| --- | --- |
| 后台到点 | 15:00 的计划在 15:00:12 收到系统回调，晚约 12 秒，无需先打开 App |
| 静音震动 | 手机处于静音，仍开始规律震动 |
| 持续运行 | 持续约 8 分 14 秒，期间没有自行结束 |
| 用户确认 | 15:08:26 进入 App 后震动停止，服务随后退出 |

这是目前方案在这台手机上的验证结果。它不等于所有手机、所有休眠条件下都保证准点；系统仍显示可延迟窗口，前台自然到点也需要单独观察验证。

## 六、以后再做类似功能，应从一开始怎么设计

1. **先明确完整行为。** 包括什么时候提醒、静音时怎样、前台时怎样、哪些操作算确认，以及什么时候必须停止。
2. **把计时交给系统。** 固定时间由系统闹钟负责，App 不靠界面一直开着计时；另做有限的补发机制。
3. **把震动的开始和停止放在一起设计。** 有统一的控制对象、清晰的运行状态和停止入口，停止后旧请求不能再次启动。
4. **尽早加上关键日志。** 至少知道计划何时、实际何时收到、是否开始震动、为什么停止。否则几种完全不同的问题看起来都会是“没有提醒”。
5. **尽早在真实后台条件下验证。** 手机静音、App 退到后台、锁屏后自然等到提醒，再确认打开 App 能停止；同时核对目标机型的后台设置。

这次最需要改进的是：**我一开始按功能点逐个实现，对完整使用过程和 Android 后台限制考虑不足，又在修复时擅自简化了前台行为。**
最后形成的做法，是把时间安排、震动控制、停止确认和设备后台设置分别处理，再用实际运行结果把它们验证起来。
